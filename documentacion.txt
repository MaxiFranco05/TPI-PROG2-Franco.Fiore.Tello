3.1. Java y JDBC

Java es un lenguaje de programación orientado a objetos, multiplataforma y
ampliamente utilizado en el desarrollo de aplicaciones empresariales. Para este
proyecto se utilizó Java 21 con Maven como herramienta de compilación y gestión
de dependencias.

JDBC (Java Database Connectivity) es la API estándar de Java para la conexión
con bases de datos relacionales. Permite ejecutar sentencias SQL, procesar
resultados y manejar transacciones de forma programática. En este proyecto se
utilizaron exclusivamente PreparedStatement para prevenir inyecciones SQL y
ResultSet para la lectura de datos.

3.2. MySQL y Bases de Datos Relacionales

MySQL es un sistema de gestión de bases de datos relacional de código abierto.
Se utilizó como motor de persistencia por su confiabilidad, rendimiento y
facilidad de configuración. El modelo relacional permite organizar los datos en
tablas con relaciones definidas mediante claves foráneas (foreign keys),
garantizando la integridad referencial.

El esquema de la base de datos incluye cinco tablas: categoria, producto,
usuario, pedido y detalle_pedido, con relaciones 1:N y N:1 que reflejan
fielmente el modelo de dominio.

3.3. Patrón DAO (Data Access Object)

El patrón DAO separa la lógica de acceso a datos de la lógica de negocio.
Consiste en una interfaz genérica que define las operaciones CRUD básicas
(guardar, buscarPorId, listarTodos, actualizar, eliminar) y una implementación
concreta para cada entidad. Esto permite:

- Aislar los cambios en la base de datos (solo se modifica el DAO).
- Reutilizar el código de acceso a datos.
- Facilitar las pruebas unitarias mediante mocks.

3.4. Transacciones en Base de Datos

Una transacción es una unidad de trabajo atómica que debe ejecutarse
completamente o no ejecutarse en absoluto (principio ACID: Atomicidad,
Consistencia, Aislamiento, Durabilidad). En el contexto del proyecto, la
creación de un pedido involucra:

1. Insertar el pedido en la tabla pedido.
2. Insertar cada detalle en la tabla detalle_pedido.
3. Actualizar el total del pedido.

Si cualquiera de estos pasos falla, todos los cambios deben deshacerse
mediante un rollback para evitar datos inconsistentes (por ejemplo, un pedido
sin detalles o un detalle huérfano).

4.1. Estructura de Paquetes

La arquitectura del proyecto sigue una división en capas bien definida dentro
del paquete base integrado.prog2:

integrad.prog2/
├── Main.java                  # Punto de entrada
├── config/
│   └── DatabaseConnection.java # Conexión centralizada a MySQL
├── dao/                        # Patrón DAO (acceso a datos)
│   ├── IDAO.java              # Interfaz genérica CRUD
│   ├── CategoriaDAO.java
│   ├── ProductoDAO.java
│   ├── UsuarioDAO.java
│   ├── PedidoDAO.java
│   └── DetallePedidoDAO.java
├── entities/                   # Modelo de dominio
│   ├── Base.java              # Clase abstracta (id, eliminado, createdAt)
│   ├── Categoria.java
│   ├── Producto.java
│   ├── Usuario.java
│   ├── Pedido.java
│   └── DetallePedido.java
├── enums/                      # Enumeradores
│   ├── Rol.java
│   ├── Estado.java
│   └── FormaPago.java
├── interfaces/                 # Interfaces de comportamiento
│   └── Calculable.java
├── exception/                  # Excepciones personalizadas
├── service/                    # Capa de servicios (lógica de negocio)
│   ├── CategoriaService.java
│   ├── ProductoService.java
│   ├── UsuarioService.java
│   └── PedidoService.java
└── ui/                         # Interfaz de usuario por consola
    ├── Menu.java
    └── MenuPrincipal.java

Decisiones clave de diseño:

- Herencia: Todas las entidades heredan de la clase abstracta Base, que
  centraliza los atributos id, eliminado y createdAt, evitando su repetición
  en cada clase.

- Interfaces: Pedido implementa la interfaz Calculable, que define el método
  calcularTotal(). Esto permite que cualquier clase que necesite calcular un
  total pueda hacerlo de manera polimórfica.

- IDAOT: La interfaz genérica IDAO define el contrato CRUD con tipos
  parametrizados, lo que permite que todos los DAOs compartan la misma
  estructura sin duplicar código.

- Separación de responsabilidades: Los DAOs solo acceden a la base de datos,
  los Services orquestan la lógica de negocio y las validaciones, y la UI
  maneja exclusivamente la interacción con el usuario.

4.3. Manejo de Transacciones

La transacción se implementa en el método guardarConDetalles() de la clase
PedidoService. El flujo es el siguiente:

1. Se obtiene una conexión desde DatabaseConnection.
2. Se desactiva el autocommit con setAutoCommit(false).
3. Se guarda el pedido (pedidoDAO.guardarConTransaccion).
4. Por cada detalle, se guarda el detalle (detallePedidoDAO.guardarConTransaccion).
5. Se recalcula el total del pedido.
6. Se actualiza el total en la base de datos.
7. Si todo es exitoso: se ejecuta conn.commit().
8. Si ocurre cualquier excepción: se ejecuta conn.rollback() en el bloque
   catch, deshaciendo todos los cambios.

Es importante destacar que se comparte la MISMA conexión (conn) entre todos
los DAOs involucrados en la transacción, ya que de otra forma cada Prepared-
Statement usaría una conexión distinta y el rollback no tendría efecto sobre
las otras operaciones.

4.4. Baja Lógica (Soft Delete)

Ningún registro se elimina físicamente de la base de datos. En lugar de usar
DELETE, todos los métodos eliminar() ejecutan:

    UPDATE tabla SET eliminado = true WHERE id = ?

Además, todos los métodos listarTodos() y buscarPorId() filtran con:

    WHERE eliminado = false

Esto garantiza que los registros "eliminados" nunca se muestren al usuario,
pero se conservan en la base de datos por si se necesita auditoría o
recuperación futura.

5. DIFICULTADES Y SOLUCIONES
================================================================================

5.1. Manejo de la Conexión en Transacciones

Dificultad: Inicialmente, los DAOs abrían y cerraban su propia conexión en
cada operación. Al implementar la transacción del pedido, los detalles se
guardaban en conexiones distintas, por lo que el rollback no deshacía los
cambios del pedido.

Solución: Se crearon métodos alternativos en los DAOs (guardarConTransaccion)
que reciben la conexión como parámetro externo, permitiendo que PedidoService
controle una única conexión a lo largo de toda la transacción.

5.2. Generación de IDs

Dificultad: Al crear objetos en memoria, necesitábamos identificarlos antes
de persistirlos para usar.equals() y contains() en las colecciones. El primer
approach fue usar un contador estático en Base, pero esto generaba IDs
inconsistentes si la aplicación se reiniciaba.

Solución: Se eliminó el contador estático y se inicializó id como null. Los
IDs ahora son asignados exclusivamente por el auto-increment de MySQL mediante
Statement.RETURN_GENERATED_KEYS. Se ajustó el método equals() de Producto
para tolerar IDs nulos usando Objects.equals().

5.3. Validación de Mail Único

Dificultad: Detectar duplicados de mail antes de insertar requería una
consulta adicional a la base de datos.

Solución: Se aprovechó la constraint UNIQUE de MySQL en la columna mail y se
capturó el error SQL 1062 (Duplicate entry) en UsuarioDAO, lanzando una
MailDuplicadoException. Esto evita una query extra y delega la validación en
el motor de base de datos.

5.4. Reintegro de Stock al Cancelar Pedido

Dificultad: Al cancelar un pedido, el stock de los productos debe
restablecerse automáticamente.

Solución: En el método eliminarPedido() de Menu.java, antes de marcar el
pedido como eliminado se recorre la lista de detalles y se suma la cantidad
de cada producto a su stock actual. Luego se persiste el cambio con
productoService.actualizar().
